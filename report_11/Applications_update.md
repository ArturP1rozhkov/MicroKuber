

### Задание 1. Выбрать стратегию обновления приложения и описать ваш выбор

1. Имеется приложение, состоящее из нескольких реплик, которое требуется обновить.
2. Ресурсы, выделенные для приложения, ограничены, и нет возможности их увеличить.
3. Запас по ресурсам в менее загруженный момент времени составляет 20%.
4. Обновление мажорное, новые версии приложения не умеют работать со старыми.
5. Вам нужно объяснить свой выбор стратегии обновления приложения.

1. Создать deployment приложения с контейнерами nginx и multitool. Версию nginx взять 1.19. Количество реплик — 5.
2. Обновить версию nginx в приложении до версии 1.20, сократив время обновления до минимума. Приложение должно быть доступно.
3. Попытаться обновить nginx до версии 1.28, приложение должно оставаться доступным.
4. Откатиться после неудачного обновления.

# Разбор решения заданий
## Задание 1
### Выбор стратегии обновления: Recreate.

Обоснование:  условие «мажорное обновление, новые версии приложения не умеют работать со старыми» означает, что приложение не может находиться в «смешанном» состоянии: поды старой и новой версий не должны существовать в кластере одновременно. Это исключает все стратегии, построенные на параллельной работе двух версий: 
- Rolling Update - в процессе обновления старые и новые поды обслуживают трафик одновременно, что нарушит совместимость;
- Canary - предполагает совместную работу основной и новой версии с распределением трафика между ними;
- A/B-тест - по своему определению обе версии работают с пользователями одновременно.

Blue-Green формально позволяет избежать совместного обслуживания трафика (переключение происходит мгновенно через Service), но требует развернуть полную копию приложения параллельно с основной - то есть 100% дополнительных ресурсов, тогда как доступный запас составляет только 20%. Значит Blue-Green также неприменим.

Стратегия Recreate удаляет все поды старой версии и только после этого создаёт поды новой версии:
- одновременной работы двух версий нет;
- дополнительных ресурсов не требуется, в любой момент времени развёрнута не более чем одна копия приложения.

**Цена решения**

Recreate приводит к простою на время удаления старых подов и запуска новых. Поэтому обновление следует выполнять в период минимальной нагрузки (в эти часы есть запас ресурсов 20%, что дополнительно снизит риски нехватки ёмкости при повторном развёртывании) и заранее уведомить пользователей о плановом техобслуживании.

Для сокращения простоя до минимума перед выкатом рекомендуется предзагрузить новый образ на узлы (imagePullPolicy / предварительный pull), чтобы не терять время на загрузку образа после удаления старых 
подов. Само обновление выполняется командой `kubectl apply` с изменённым образом, контроль состояния (`kubectl rollout status deployment/<имя>`).

Если в будущем простой станет неприемлемым, потребуется либо пересмотреть требование несовместимости версий на уровне приложения (обратно совместимые API и схемы БД, тогда станет доступен Rolling Update), либо увеличить ресурсы кластера (тогда станет доступен Blue-Green с мгновенным переключением трафика).

## Разбор решения задания 2

Важное уточнение: задание написано с с условием того, что версии **nginx 1.28 не существует**, и обновление на неё должно провалиться. Но стабильная ветка nginx 1.28.0, и образ `nginx:1.28` вышли в апреле 2025 года и сейчас реально есть на Docker Hub. То есть обновление до 1.28 **успешно пройдёт**, и сценарий «неудачное обновление - откат» воспроизвести не получится. Поэтому для демонстрации этого сценария возьму **несуществующий тег**, например `nginx:1.28.100` (последняя версия в этой ветке - 1.28.3).

### Создал файл-манифест `deployment.yaml`:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-multitool
  labels:
    app: nginx-multitool
spec:
  replicas: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 5         
      maxUnavailable: 0   
  selector:
    matchLabels:
      app: nginx-multitool
  template:
    metadata:
      labels:
        app: nginx-multitool
    spec:
      containers:
      - name: nginx
        image: nginx:1.19      
        ports:
        - containerPort: 80
          name: http
      - name: multitool
        image: wbitt/network-multitool
        env:
        - name: HTTP_PORT      
          value: "8080"        
        ports:
        - containerPort: 8080
          name: mt-http
---
apiVersion: v1
kind: Service
metadata:
  name: nginx-multitool-svc
spec:
  selector:
    app: nginx-multitool
  ports:
  - port: 80
    targetPort: 80
    name: nginx
  - port: 8080
    targetPort: 8080
    name: multitool
```

- Deployment: nginx 1.19 + multitool, 5 реплик. Стратегия: RollingUpdate с maxSurge=5 / maxUnavailable=0 
- image: nginx:1.19  - начальная версия
- Service - проверка доступности приложения во время обновлений
- maxSurge: 5 - поднять сразу все 5 новых подов параллельно
- maxUnavailable: 0   - старые поды не трогаем, пока новые не станут Ready
